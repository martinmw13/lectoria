# Task: an "Apply" button for the friend code, with instant server feedback

Context: on prod a reader types the friend code, presses Enter, and nothing happens. Today the code (app/home/friend-code.tsx `FriendCode`, state in app/home/upload.tsx) is only checked by the server when an upload starts (server/uploads/handler.ts calls `acceptFriendCode` from server/guard/quota.ts with `friendGuessKeyFor`). The welcome line `FRIEND_WELCOME` (Spanish copy is intended, keep it exactly) currently shows only after the create response says `friendAccepted: true`.

1. Server: new endpoint `POST /api/uploads/friend-code` (thin route file app/api/uploads/friend-code/route.ts, `runtime = "nodejs"`, logic in a new server/uploads/friend-code.ts handler `handleFriendCodeCheck(req, deps)` with injectable `env`/`kv`/`now` for tests). Order: `rejectsCrossSite` → small body cap via `readBodyCapped` (e.g. 1024 bytes) → strict JSON parse of `{ code: string }` (anything else → `{ ok: false }` with 400, no details) → env via `readUploadEnv` (missing → 503 `{ ok: false }`, no names logged) → anon cookie like `ensureAnon` in handler.ts (reuse/extract it rather than duplicating if trivial) → `acceptFriendCode(kv, code, env.friendCodes ?? [], friendGuessKeyFor({ day, ip, salt: env.ipSalt, anonId }))`. That gives the same constant-time compare and the same 10-wrong-guesses-a-day limiter per hashed IP. Respond 200 `{ ok: boolean }` only. Never echo, log or store the code; no raw errors; console logs at most a fixed word like "friend-code check failed" on an unexpected throw (respond 503 `{ ok: false }`). Feature off (no codes) → `{ ok: false }`. No Turnstile needed (the guess limiter caps it). Set any anon cookie on the response.
2. Client: app/home/friend-code.tsx gets an "Apply" button next to the input (boxless quiet style like `.ob-quiet`, still reads as clickable) and Enter in the input applies it. Enter must `preventDefault()` and not submit any surrounding form or trigger the file input/dialog (check whether the friend field sits inside a `<label>` or form tied to the file input, and fix that so a click/Enter on the field never opens the file picker). A small client helper (e.g. `checkFriendCode(code, fetchFn = fetch)` in app/home/friend-code.ts or the same file) POSTs `{ code }` to the endpoint, returns `true` only for a 200 with `ok === true`, false for anything else (network error included). While checking, disable the button (label "Checking…"). On ok: call a new `onAccepted()` prop so upload.tsx sets `friendWelcome` true right away and keeps the code in state for the upload (show the same `<p className="ob-friend-ok" role="status">{FRIEND_WELCOME}</p>` light-blue note right under the field). On fail: show a warm `That code didn't work.` (role="status", muted, no red alarm) and keep friendWelcome false. Editing the code after a result clears the result (and sets friendWelcome back to false). The upload still sends the code and the server still re-validates it at create; keep the existing create-response handling. Empty code: Apply disabled.
3. Tests (mock fetch/KV; no network): server handler (valid code → `{ok:true}`; wrong code → `{ok:false}` and the guess counter goes up; after 10 wrong guesses even the valid code → false; bad JSON / non-string / cross-site → `{ok:false}` 400; feature off → false; response body never contains the code); client (Apply click and Enter both call the endpoint once with the code; ok shows FRIEND_WELCOME exactly; fail shows "That code didn't work."; Enter does not open the file input — e.g. spy on the file input's click — and does not submit a form; empty code keeps Apply disabled). Keep each test file under the 5000-token size limit; make new small test files rather than growing big ones. app/home/upload.tsx is near the limit (about 4.8k tokens): put new logic in friend-code.tsx, not upload.tsx.
